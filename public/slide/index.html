Invoice reconciliationagainst a standard that learns.

Cloudflare Singapore Developers Day · 27 August 2026 · Bryan, Cyrus, Michelle, Siva, Zuriel

The problem

A supplier sends an invoice as a PDF.Somebody checks it by hand.

They open it next to a price list and go line by line. Is that the right SKU. Is that the contracted price. Is that the right unit of measure.

Slow

Every line, every invoice, every month. The work scales with the supplier's catalogue, not with the value of checking it.

Error-prone

A price per case billed per unit survives a tired reader. That is where the money actually hides.

Forgotten

The hard-won knowledge that this vendor calls SKU-4471 a Widget Pro 2K evaporates the moment the check is done.

The third one is the real problem. The same person solves the same puzzle every month.

The product

Upload an invoice. Decide what is wrong. The standard remembers.

  1. Parsed to structured JSONWorkers AI converts the PDF, DOCX, XLSX or image to Markdown, then extracts it into a schema-constrained invoice.
  2. Every line matched against the standardExact SKU, then a known vendor alias, then description similarity. First hit wins.
  3. Every field difference flaggedWith the money at stake spelled out, not just a red mark.
  4. A person accepts, rejects or editsNever the model. The model reads and compares; it does not decide.
  5. Accepted corrections write backThe corrected price, and the vendor's odd wording kept as an alias.
  6. A corrected invoice is publishedShowing exactly which lines moved, and by how much.

The payoff

It flags plenty on the first invoice.It has less to flag on the second.

Invoice A
8 decisionsUnrecognised names, a stale price, a unit of measure billed wrong.
Write-back
alias + priceThe vendor's wording is stored against the SKU. The catalogue version bumps.
Invoice B, same vendor
tier 2, not tier 4The same wording now hits a known alias instead of asking a person.

That is the demo: a catalogue that gets better every time a person touches it. The model only does the reading.

Architecture

One Worker, one deploy.

The matching ladder

Four tiers, first hit wins.Cheap before clever.

1
Exact SKU

The line carries a SKU and it is in the catalogue. Free, and it covers most lines.

score 1.00
2
Known alias

The normalised description hits a wording this vendor has used before. This tier is what the write-back grows.

score 0.95
3
Description similarity

Embed the description and take the nearest catalogue entry above threshold. Only reached when the first two miss.

threshold 0.82
4
No match

Nothing corresponds. Every field is flagged unmatched and a person assigns a SKU, which teaches tier 2.

needs a person

Tier 2 is the whole product. Every correction a reviewer accepts moves a future line from tier 3 or 4 up to tier 2, where it costs nothing and asks nobody.

The diff

Where the money actually hides.

Each flag states the delta and the money at stake across the quantity, because that is the number a reviewer is deciding about.

FieldRuleWhy it matters
unitPriceDiffers from the list price by more than 0.5%The obvious one. Small percentages across large quantities.
uomAny difference at allA price per case billed per unit. This is the expensive one and it reads as a typo.
descriptionNot the canonical name and not a known aliasThe one whose acceptance teaches the system. Cheap to resolve, compounding value.
lineTotalRecomputed as quantity × unitPricePlain arithmetic errors on the document.
taxCodeDiffers from the standard's codeQuiet, and it propagates into the filing.

The learning loop

Three decisions.Only two of them touch the catalogue.

Correct the invoice

The standard was right. The corrected value goes into the published invoice. The catalogue is untouched, because it had nothing to learn.

Update the standard

The standard was stale. The price is updated, the version bumps, the vendor's wording is stored as an alias, and an audit row is written.

Enter different values

Neither side was right. A person types a third value. Same write-back path, with the actor recorded.

Getting this backwards would have the system learn from the invoices it just rejected. It is the one rule in the codebase worth stating twice.

Why a Durable Object

Two reviewers, one session, no lost edits.

The session is shared state that several people edit while a document is being processed against it. That is the one problem a Durable Object solves and a database does not.

One object per review

It holds the session and serialises edits, so two reviewers racing on the same line cannot overwrite each other. The catalogue lives in D1, not here: two reviewers updating the same SKU is a different problem with a different owner.

Hibernation, not a held socket

The WebSocket Hibernation API hands the socket to the runtime, so the object sleeps between messages and still wakes to deliver one. An object holding an open connection bills for idle time and eventually drops it anyway.

Then
1 persistAn object can hibernate between any two awaits.
Then
2 write backThe catalogue and its audit row.
Only then
3 broadcastTell the other browsers what actually landed.

Broadcast first and the other screen is told a thing landed that may not have. The reviewer sees a lie and the next invoice does not learn.

The output

A corrected invoice,and proof it was corrected.

As invoiced
4,325.34The supplier's own stated total, not our re-addition of their lines.
As corrected
4,255.58Corrections applied as a delta, so header adjustments survive.
Difference
-69.76Overstated, across 4 lines, on the demo invoice.

Every changed field is marked

The corrected value with the supplier's original struck beneath it, and the reason it moved. A line total recomputed from a corrected unit price says exactly that, rather than borrowing an unrelated flag's wording.

The version stamp is checkable

A SHA-256 over the corrected invoice, excluding the timestamp. Re-render with nothing decided and the digest is identical; correct one line and it moves. A timestamp alone proves nothing about content.

Money is held in integer cents end to end, and the tax rate is derived from the document's own stated figures rather than hardcoded. A document whose arithmetic is visibly wrong is worse than no document.

What we cut, and why

One is bound and reachable.It is not doing work yet.

We wrote a drop ladder before we started and then followed it. This one sat at the top, and it is the only rung we never had to climb back down.

ServiceStatusWhat we did instead
Queuesbound, unusedBulk upload never became the story. One invoice at a time carries the demo.

Three rows left this table during the build rather than joining it. The matcher and the write-back landed late but real: the ladder runs live against the KV snapshot with D1 as fallback, semantic match hits Vectorize above the 0.82 floor, and an audit row claims persisted only after its D1 write succeeds. Browser Run went the same way: publish renders a real PDF into R2, and the print stylesheet is now the fallback rather than the plan.

We would rather tell you one binding is idle than dress it up as load-bearing.

Demo

One invoice, end to end.

  2. Three flags fireA stale price, a unit of measure worth real money at that quantity, and a product name nothing recognises.
  3. DecideCorrect the invoice on one. Update the standard on another. The standard was out of date; now it is not.
  4. Show the audit trailEvery change, who made it, when, and from what to what.

  6. Then invoice BSame vendor, same odd wording. The names that needed a person last time hit the alias tier this time. That is the standard proving it learned.
